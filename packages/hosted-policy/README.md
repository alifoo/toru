# Hosted policy — private

This package contains commercial policy for the hosted Recorder service. It is not part of the MIT engine distribution and is not published to a registry. No Stripe key or external service is needed to test the transactional ledger locally.

`CreditLedger` receives the engine's transactional SQLite store through a structural interface. It creates separate hosted tables in the same database so later admission/job updates can share a transaction. Accounts must already exist; this module never silently provisions a user.

Current implementation covers the proposed Free policy only: ten videos per UTC calendar month, a single reserved credit per job, idempotent commit on first delivery, release without delivery, and immutable audit entries. A month boundary does not move an existing reservation to a new bucket. Delivery after expiration consumes the original bucket. Downloads/rerenders must never call reserve for another video. A released reservation is terminal; recoverable render failures should keep their reservation until recovery or explicit abandonment.

The private `apps/hosted` runtime injects this policy through generic engine lifecycle hooks. Admission and job state share a SQL transaction. First MP4 delivery commits once; failed startup/abandoned uncaptured work releases the credit. Recoverable raw capture retains its reservation. File publication uses a durable intent with checksum/size, followed by file fsync and an atomic job/ledger commit; restart reconciles pending publication without browser replay. Limits are 10-minute sessions, 2-minute capture, two successful presentation rerenders, 24-hour raw and 7-day MP4 retention. Failed rerenders do not consume the allowance. `account_usage` exposes the authenticated balance. The engine deduplicates render requestIds durably and the console reads balances through an owner-scoped server route. Paid entitlement changes, provider reconciliation, detailed usage history and durable queue remain incomplete. The schema reserves bucket sources for future paid/admin policy; it does not implement purchasing or paid subscriptions.

`BillingEventInbox` is a separate private SQLite receipt store for Stripe events **after** raw-body signature verification by the hosted HTTP adapter. It scopes receipts to one Stripe account and mode, deduplicates by event ID, retains only a body hash and object reference, and lists pending events for provider-state reconciliation. `processPending` runs the SQLite billing callback and receipt completion in one transaction, rolling both back if the callback fails. `StripeStateReader` checks the configured account, retrieves the event, then reads the current invoice, subscription or Checkout Session; it never grants credits. Checkout and entitlement processing remain disabled until checkout creation, product/price validation, lifecycle handling and sandbox tests are complete.

`BillingCustomers` now creates durable, idempotent checkout intents for admitted accounts and binds a completed Stripe customer only when the current Checkout Session matches that intent, the Recorder product metadata, account mode, session creation window and owner. `reconcileCheckoutBindings` reads only pending `checkout.session.completed` receipts, then binds the customer and completes the receipt in one SQLite transaction; unrelated invoice events remain pending. These components do not grant paid credits or run on a schedule. Keep checkout disabled until the authenticated route, entitlements and provider sandbox lifecycle are validated.

`StripeCheckoutClient` prepares a hosted Creator Checkout Session from an existing intent. Before POST it verifies the Stripe account, exact monthly licensed Price (amount/currency/product/mode) and the active Product's `product=agent-recorder` metadata. It sends a stable Stripe idempotency key and server-defined product/intent metadata on the Session and Subscription. The result is accepted only if it points to Stripe Checkout with the same intent and mode. The private hosted service exposes a test-mode-only admin route; it is disabled by default, unavailable in production/live mode, and not called by the console. No real Stripe API request or charge was made in these tests.
